# CTCL-ITR v0.2.3 Governance Core Design

## Goal

Add a dependency-light governance layer that turns human checkpoints into explicit, auditable runtime objects without changing canonical TemporalEvent semantics.

## Core objects

### ApprovalRequest
Represents a decision-ready request for human governance.

Required fields:
- `approval_id`
- `run_id`
- `intent_id`
- `trigger_event_id`
- `requested_action`
- `target`
- `risk_class`
- `reason`
- `options[]`
- `evidence_refs[]`
- `authority_requested`
- `requested_at`
- `expires_at`

### DecisionReceipt
Represents what a human decided and the human governance cost.

Required fields:
- `decision_id`
- `approval_id`
- `run_id`
- `principal`
- `decision`
- `selected_option`
- `decided_at`
- `human_active_ms`
- `human_governance_ms`
- `reason?`

`decision` is one of `approve`, `deny`, `modify`, `defer`, `cancel`.

### AuthorityGrant
Represents the bounded execution authority created by an approved decision.

Required fields:
- `authority_ref`
- `decision_id`
- `principal`
- `scope[]`
- `target`
- `issued_at`
- `expires_at`
- `max_uses`
- `revocable`

An approval does not itself equal authority. A grant is emitted only when the decision and requested authority are compatible.

## State machine

```text
requested -> pending
pending -> approved | denied | modified | deferred | cancelled | expired
approved | modified -> authority_grant? -> consumable
```

Authority use:

```text
active -> consumed | revoked | expired
```

## Resume eligibility

A suspended run may resume only when:
1. the ApprovalRequest is resolved with `approve` or compatible `modify`;
2. the DecisionReceipt is not expired relative to the request;
3. the AuthorityGrant is active;
4. requested action and target are within grant scope;
5. remaining use count is positive.

The reference function returns a structured report, not a boolean only.

## Event integration

Canonical TemporalEvent remains unchanged. Governance objects are referenced from existing event payloads:

- `human.checkpoint.requested` -> `approval_id`
- `human.checkpoint.resolved` -> `decision_id`
- `authority.checked` -> `authority_ref`
- `run.resumed` -> `decision_id`, `authority_ref`

## Queue semantics

The reference `ApprovalQueue` is in-memory and deterministic. It supports:
- enqueue
- get pending requests
- resolve
- expire due requests
- lookup receipt / grant

It is a reference semantic core, not a distributed queue.

## Non-goals

- no Slack/Gmail/UI transport;
- no cryptographic human identity proof;
- no multi-party approval quorum;
- no persistent DB queue;
- no automatic policy engine;
- no replacement of AICL authority governance.

## Compatibility

- TemporalEvent schema remains unchanged;
- v0.2.0 topology stays unchanged;
- v0.2.1 observability projections stay unchanged;
- v0.2.2 integrity records hash governance events exactly as ordinary ATL events.
