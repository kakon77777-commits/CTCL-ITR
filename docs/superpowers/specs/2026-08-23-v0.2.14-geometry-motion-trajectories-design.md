# CTCL-ITR v0.2.14 Geometry Motion Stability & Multi-Snapshot Trajectories — Design

**Status:** approved for implementation
**Date:** 2026-08-23

## Goal

Extend the read-only v0.2.13 pairwise geometry-drift layer from two compatible geometry observations to an ordered trajectory of three or more observations without changing calibration, resampling, surface, geometry, or authorization semantics.

## Canonical frame

The reference trajectory keeps one baseline snapshot fixed and compares three observations:

```text
G0 = Geometry(base -> current)   at 2026-08-23T00:00:00Z
G1 = Geometry(base -> later)     at 2026-08-24T00:00:00Z
G2 = Geometry(base -> regressed) at 2026-08-25T00:00:00Z
```

`G2` deliberately reuses the `current` evidence profile under a new observation identity and the same deterministic resampling seed. It is a regression/reversal test fixture, not a forecast.

## Architecture

New module `ctcl_itr.calibration_geometry_trajectory` validates an ordered v0.2.14 trajectory spec and a same-length list of v0.2.12 geometry reports. Every geometry must satisfy the same v0.2.12 measurement/grid/boundary contract. Consecutive observations are compared through the existing v0.2.13 `compare_surface_geometry()` function; v0.2.14 aggregates those pairwise results into multi-snapshot trajectory diagnostics.

## Time contract

Observation timestamps are explicit in the trajectory spec and must be strictly increasing ISO-8601 timestamps. Durations are reported in seconds and days (`86400 s`). Boundary velocity is finite displacement divided by elapsed days. Boundary acceleration is a finite difference between consecutive velocity segments divided by the average of the adjacent segment durations.

These are descriptive measurement-space derivatives, not physical or causal velocities.

## Outputs

### Stepwise drift chain

For every consecutive observation pair, emit IDs, elapsed time, supported-domain change, split/merge counts, positive-boundary displacement, support-frontier displacement, and local-gradient drift summary.

### Support trajectory

For each subject emit:

- supported-cell count series;
- consecutive count deltas;
- direction (`expansion`, `contraction`, `flat`);
- non-zero direction reversal count;
- net / minimum / maximum supported count.

### Boundary lineages

Positive and negative stability boundaries are linked only through the deterministic v0.2.13 consecutive nearest-L1 matches. A lineage is a connected chain of those descriptive matches. Emit:

- first/last observation;
- observation count and lifespan days;
- ordered points;
- per-step signed family velocity and L1 speed per day;
- finite-difference acceleration;
- per-family velocity-direction reversal counts;
- total path L1 and net signed displacement;
- whether the lineage spans all observations.

`Boundary Lineage != Persistent Boundary Identity` remains explicit.

### Component lineages and lifespan

Supported components are linked through v0.2.13 component member-overlap links. Emit weak lineages with first/last observation, observation count, lifespan, component nodes, and branch/merge counts. Component lineages are descriptive overlap histories, not persistent object identity.

### Sign-region persistence

For the union of supported cell keys across observations, emit each cell's sequence of `positive_band`, `negative_band`, `crosses_zero`, `zero_band`, or `unsupported`. Summarize:

- supported in all observations;
- positive in all observations;
- cells whose class changes;
- support excursions (`unsupported -> supported -> unsupported` or the inverse pattern across >=3 observations);
- maximum consecutive positive-band run.

### Gradient trajectories

Track local-gradient edges by the canonical sorted edge key across observations. Emit slope series, presence series, persistent-all-observations flag, appeared/disappeared counts, point-slope step changes, mean/max absolute change, and reversal count in non-zero slope-change direction.

## Canonical reversal case

The canonical trajectory intentionally yields:

```text
supported cells: 6 -> 8 -> 6
support directions: expansion -> contraction
support reversal count: 1
```

The positive stability boundary moves from the v0.2.12 current geometry to the v0.2.13 later geometry and then returns to the original current position, producing a finite-difference velocity-direction reversal.

## Epistemic boundary

```text
Geometry Trajectory != Causal Mechanism
Finite-Difference Boundary Velocity != Capability Velocity
Finite-Difference Boundary Acceleration != Physical Acceleration
Support Reversal != Universal System Regression
Boundary Lineage != Persistent Boundary Identity
Component Lineage != Persistent Component Identity
Gradient Trajectory != Global Derivative Field
Trajectory Report != Authority
```

No trajectory output grants, revokes, suspends, resumes, or commits authority.

## Compatibility

- v0.2.13 geometry-drift semantics unchanged;
- v0.2.12 surface geometry unchanged;
- v0.2.11 joint surface and earlier calibration/uncertainty layers unchanged;
- no TemporalEvent/governance schema change;
- no new runtime dependency.
