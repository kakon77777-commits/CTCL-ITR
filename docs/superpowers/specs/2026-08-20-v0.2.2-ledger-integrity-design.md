# CTCL-ITR v0.2.2 Ledger Integrity Design

## Goal

Add a tamper-evident integrity layer for ATL JSONL ledgers without changing canonical TemporalEvent semantics.

## Architecture

v0.2.2 uses a **sidecar hash chain** rather than embedding recursive digest fields in TemporalEvent objects. Each event record produces one `IntegrityRecord`; the final chain head is summarized by a `LedgerAnchor`.

```text
ATL JSONL record bytes
        ↓ SHA-256
   record_digest
        + previous_chain_digest
        ↓ domain-separated SHA-256
    chain_digest
        ↓
IntegrityRecord JSONL
        ↓ final head + count
    LedgerAnchor JSON
```

The event ledger remains canonical execution history. Integrity metadata is derived evidence about that history.

## Threat Model

v0.2.2 detects:

- modification of an event record;
- event reordering;
- interior deletion/insertion relative to an existing chain;
- event/integrity sidecar mismatch;
- suffix truncation **when checked against a trusted anchor**.

v0.2.2 does **not** claim protection against an attacker who can rewrite the event ledger, integrity sidecar, and trusted anchor together. External signing/publication of anchors is deferred.

## Record Encoding

The reference profile hashes exact JSONL **record bytes excluding the line terminator**. Blank lines are rejected.

Profile identifier:

```text
atl-jsonl-record-v1
```

This intentionally provides byte-level tamper evidence. It does not claim RFC 8785 semantic canonicalization. RFC 8785 remains a future interoperability option for canonical semantic hashing.

## Digest Rules

Hash algorithm:

```text
sha256
```

Event record digest:

```text
record_digest = SHA256(record_bytes)
```

Chain digest:

```text
chain_digest = SHA256(
    b"CTCL-ITR/ATL/CHAIN/v0.2.2\0"
    || previous_chain_digest_raw_32_bytes
    || record_digest_raw_32_bytes
)
```

Genesis previous digest is 32 zero bytes.

Digest text representation:

```text
sha256:<64 lowercase hex chars>
```

## IntegrityRecord

```json
{
  "schema_version": "0.2.2",
  "run_id": "run:demo",
  "ledger_seq": 1,
  "event_id": "evt_001",
  "hash_algorithm": "sha256",
  "record_encoding": "atl-jsonl-record-v1",
  "record_digest": "sha256:...",
  "previous_chain_digest": null,
  "chain_digest": "sha256:..."
}
```

For records after genesis, `previous_chain_digest` MUST equal the prior record's `chain_digest`.

## LedgerAnchor

```json
{
  "schema_version": "0.2.2",
  "run_id": "run:demo",
  "event_count": 12,
  "first_event_id": "evt_001",
  "last_event_id": "evt_012",
  "hash_algorithm": "sha256",
  "record_encoding": "atl-jsonl-record-v1",
  "final_chain_digest": "sha256:..."
}
```

The anchor detects suffix truncation only when the verifier receives the expected anchor from a trust boundary not silently rewritten with the ledger.

## Verification Report

`verify_ledger(...)` returns a structured report:

```json
{
  "valid": true,
  "event_count": 12,
  "checked_records": 12,
  "anchor_checked": true,
  "head_digest": "sha256:...",
  "failure": null
}
```

On failure:

```json
{
  "valid": false,
  "failure": {
    "code": "record_digest_mismatch",
    "ledger_seq": 6,
    "event_id": "evt_006",
    "message": "..."
  }
}
```

First-failure reporting is sufficient for v0.2.2.

## CLI

```bash
ctcl-itr-integrity seal EVENTS.jsonl \
  --chain-out EVENTS.integrity.jsonl \
  --anchor-out EVENTS.anchor.json

ctcl-itr-integrity verify EVENTS.jsonl \
  --chain EVENTS.integrity.jsonl \
  --anchor EVENTS.anchor.json
```

`verify` prints JSON. Exit code is `0` for valid, `1` for integrity failure, `2` for malformed invocation/input.

## Acceptance Tests

1. Same record bytes produce the same SHA-256 digest.
2. Seal + verify passes on the reference ledger.
3. Mutating one event byte fails verification.
4. Reordering events fails verification.
5. Interior deletion fails verification.
6. Truncating both ledger and sidecar may remain internally chain-valid without anchor, but MUST fail against the original anchor.
7. Integrity sidecar schemas validate.
8. CLI seal/verify returns documented exit codes.
9. Existing v0.1/v0.2/v0.2.1 tests remain green.
10. Pack validator verifies committed integrity artifacts against fresh regeneration.

## Standards Boundary

- SHA-256 is used as specified by the Secure Hash Standard family.
- RFC 8785 demonstrates why invariant canonicalization matters for cryptographic JSON operations; v0.2.2 deliberately hashes immutable wire-record bytes instead of claiming JCS conformance.
- RFC 9162 Certificate Transparency is a stronger Merkle-log design for scalable inclusion/consistency proofs. v0.2.2 is a simpler linear hash chain; Merkle proofs are out of scope.
